# 马克听数据系统 10-01 ~ 11-23 故障与优化复盘

> 覆盖范围：五个数据工作区（荣威 b2 / MDD b5 / 特斯拉 b6 / 东风 b7 / 格力 b8）的采集、落库、看板全链路。
> 复盘目的：把两个月的踩坑沉淀成机制，明确"哪些已经根治、哪些还在带病运行"。

## 一、两个月的主线：从"天天救火"到"节奏定版"

**10 月上中旬（建设期）**：导入链路打磨——底表全量同步语义（覆盖/缺席剔除/停用恢复）、东风占位 UID 回填、大区筛选导出、MDD 口径改造（自然三数/漏斗/投流总览三口径）。

**10 月下旬（会话危机期）**：平台风控升级，会话寿命从"几天"跌到"24h"再到"15~40h 随机"，一度全线覆没。期间完成三件基础设施：partner 本地保活闭环、专业号本地保活 + `daily-login.cmd` 每日例程、企微告警体系（**webhook 至今未配，告警出口仍是断的**）。

**11-01 定案**：静默对照实验证明 partner 会话快死是**账号级风控标记**（真人 Chrome 手动登录照样 50 分钟死，换服务器/改指纹/IP 对齐全部无效），用户拍板"**一天一拖为长期常态**"。

**11-02 架构定稿**：发现风控元凶=每天 7~8 次登录事件（backend 无头重登 + cron 账密空转）。改成 **pull-t1 编排器 + 服务器端零登录**：每天唯一一次人工拖块（21:30），登录即拉数、凌晨/白天 cron 只做静默补拉。

**11-07/11-08 时刻表定版**：实测各平台 D-1 出数时刻后，deploy crontab 定版 20 行（00:40/12:40/14:10 商业内容补拉、04:00/09:00 专业号线索、07:10+13:10 投流笔记、13:15 MCC NDS 兜底等），确立"8 点前 SLA"与"物理不可能"的边界话术。

**11 月中下旬（收获期）**：11-13~11-20 连续九天落库矩阵全绿；11-20 服务器体检根治内存瓶颈（notes_daily 流式化、NODE_OPTIONS 注入、磁盘 80%→72%）；11-21 JGN 晨间波次首次整波命中。

## 二、重大故障清单（按根因分类）

### 1. 会话风控类（贯穿全程的头号敌人）
| 时间 | 事件 | 根因 | 处置 |
|---|---|---|---|
| 10-24~31 | MCC 四家+partner 反复集体 401 | 寿命缩至 15~40h | 一天一拖模型 |
| 11-01 | partner 登录后 70min 即死 | 账号级风控标记（实验定案） | 接受常态，登录即拉数榨干价值 |
| 11-02 | 服务器无头重登顶掉人工会话 | backend 每小时重登 | 摘除 PARTNER_LOGIN 凭据，服务器零登录 |
| 11-10 | 全天断档（pro 也死） | pro 寿命数周常态被打破 | pro 扫码复活，纳入保活 |
| 11-11~11-14 | 四晚例程全废（表象：秒败） | **终极根因=例程文件被 sed 损坏**（见编码类） | node 字节级修复 |
| 11-22/23 | partner 401↔200 抖动、四家 MCC 集体过期 | 正常寿命到期 + 例程漏跑 | 上午补拖 partner；**MCC 待今晚例程** |

**教训**：探活有效≠身份正确≠拉数正确；真实拉取结果才是唯一事实（SparkSyncLog / DB 真值对账）。

### 2. 静默失败类（最阴险的一类）
- **坑①**：login.cjs 失败后 push-state 仍无条件推旧 state（制造"假登录"）——本次例程改造已在 cmd 层堵死：登录失败/身份不符直接跳过推送。
- **坑③**：trigger-sync 客户端挂起/报错但后端实际成功——成败一律以 SparkSyncLog 和 DB 真值为准。
- **坑④**：星火登录页 React 双渲染出两套表单，自动填账密进隐藏表单→滑块永不弹（荣威 3 连败根因）。
- **坑⑥**：pull-t1 日志属主 root，deploy 身份跑在日志重定向处秒退且无痕迹——判据=日志无 start 行。
- **git 权限位**：Windows 提交的新脚本缺 x 位，服务器 cron 拒绝执行且零日志（11-09 三层修复：chmod+git update-index+deploy.sh 兜底）。
- **探活假阳性**：页面状态码对 SPA 登录墙必假阳（11-03 改打真实业务 API）；300013 限流会误判成会话死；partner 探活 401 但 campaign 同步照常成功（401↔200 抖动）。

### 3. 编码/工程红线类
- **sed 毁 GBK 批处理（11-15 定性，11-11~11-14 四晚例程全废的终极根因）**：Git Bash sed -i 剥掉 CR→LF 解析异常→%NODE% 丢失→Electron 秒退→登录从未发生→坑①推旧 cookie。**红线已固化为机制：本次 daily-login.cmd 重写为纯 ASCII+CRLF，这个雷区永久拆除。**
- `tsc | tail && echo OK` 掩盖失败，曾把编译失败的代码推上线（构建被 deploy 拦住才没炸生产）。
- deploy.sh `reset --hard` 会用 git 权限位覆盖服务器原位 patch——服务器 patch 必须回收入库。

### 4. 数据正确性类
- **早产零行**：平台未出数时 stat-daily 写下 impNum=0 行，早期跳过逻辑会把它永久冻结（10-31 发现，跳过条件改为要求 impNum>0）。
- **部分明细冻结（11-22 新发现）**：合计行拿到满值但逐笔记明细只有部分行（平台分页未铺满）→ 合计行>0 触发幂等跳过 → 部分行永久冻结。当日已用 STAT_FORCE 单日重拉补全（3968 行）；**巡检要点=逐笔记行数 << 合计行 noteNum 时当天必须补拉**。
- **月段深分页缺半**：sync-juguang 历史全窗拉取只落 ~45%（11-01 实验定案），近 10 天改逐日段根治。
- **口径地雷**：day 桶两种语义并存（16:00 桶 vs naive 零点），查错列/查错桶会静默查空；星火员工绑定 10-05 才生效（此前员工指标全 0 是真实数据非 bug）；MDD 停投期 fetched=0 非故障。

### 5. 人因类（本次根治）
- **串号事故两次（10-26）**：弹窗窗口长得一模一样，东风窗口输进 MDD 账密——直接推动本次"品牌护栏"改造（见第四节）。
- 漏跑例程：11-22 晚未跑 → 四家 MCC 11-22 数据缺失、次晨波次全废。**漏拖=MCC cookie 老化直接威胁次日 04:00 波次**，这句话两次被验证。

## 三、优化成果清单（已上线并验证）

1. **pull-t1 登录即拉数编排器**（11-02）：登录后自动 stat-daily 7 天窗 → KoxNote → trigger-sync → sync-juguang → MDD 四链，把人工拖块的价值当天榨干。
2. **探针式智能拉取**（11-09）：每 30 分钟轻探针，平台一放数几分钟内落库，替代固定重试槽；PROBE_RESULT 自动沉淀出数时刻档案。
3. **时刻表 20 行定版**（11-08）：凌晨/白天/兜底三层波次，配合"平台出数时刻实证表"。
4. **notes_daily 流式化**（11-20）：逐页落库 RSS 平直 287MB，根治 3.6G 机的 OOM（此前堆死过 2 次）。
5. **专业号探活 v2**（11-03）：探活打真实业务 API（获客工具统计），假阳性根治。
6. **格力全链路复活**（11-11~11-20）：orgCode 初始化、台账 30 账号对齐、NDS 回补至 8-01（49.4 万行单日窗口法）、KoxNote 元数据 661 篇补齐、笔记口径收敛为监控账号。
7. **服务器体检三件套**（11-20）：内存流式化 + NODE_OPTIONS=2048 注入 + 磁盘 80→72%。
8. **口径改造系列**：投流总览三口径、运营总览投放线剔官号（防乐允 kos_author 双计）、内容表现/投流笔记大区筛选+导出、特斯拉投流笔记明细页。

## 四、本次例程改造（11-23 上线，commit 0e3f580）

**痛点**：每个登录窗口长得一模一样，品牌信息只在 CMD 小字里，用户经常输错其他品牌的账密（历史两次真实串号事故）。

**三道防线**：

1. **预告弹窗**：每个 MCC 登录窗口弹出前，先来一个置顶确认框——大字显示品牌名、自动填入的账号、操作提示，点"确定"才开窗口。
2. **窗口内品牌护栏**：登录窗口的**标题栏**和**页面顶部红条横幅**都写明"当前窗口：荣威 RW · brand2 ｜ 账号(已自动填入)：xxx@163.com"，每次导航自动重挂（页面自己改标题也会被拨回来）。
3. **身份闸门**：登录完成立刻对账（state 里的 userName vs 品牌预期：荣威=原山互创、MDD=mkt数据、东风/格力=MKT数据）；不符则标红报警，且 **push-state-to-prod 在推送前再拦一道**——串号的 cookie 永远到不了生产库。已实测拦截分支与放行分支。

**附带修复**：
- daily-login.cmd 重写为**纯 ASCII + CRLF**——11-15 的 sed 毁 GBK 事故在这类文件上永久绝迹；
- 登录失败/身份不符 → 自动跳过推送并暂停提示（堵住"坑①推旧 cookie"）；
- 格力恢复纳入每日例程（11-11 拍板的维护范围，旧文件因 sed 事故仍停留在跳过状态）；
- 紧急跳过某品牌仍支持：运行前 `set SKIP_GREE=1`。

## 六、机制层的三条总结

1. **平台行为不可控，节奏要跟着实测走**：出数时刻、会话寿命都是漂移的——探针档案 + 落库时间戳是唯一可信依据，"以前是这样"不算数。
2. **静默失败是最大风险面**：每条链路都要有"失败会大声说话"的出口（告警 webhook、身份闸门、推送拦截、日志 start 行判据）。
3. **人工操作要给防呆**：窗口长一样就必然串号，文件编码有红线就必然被踩——本次品牌护栏和 ASCII 化就是把"依赖人小心"改成"结构上不可能错"。
