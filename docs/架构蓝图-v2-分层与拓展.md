# 架构蓝图 v2:分层目标架构(结构化 + 可拓展)

> 2026-11-24。本文回答"要一个更结构化、更可拓展的系统"。
> 结论:**借鉴市场成熟模式的"契约与分层",不引入它们的软件**。数据源是对抗性平台(cookie 会话、
> 风控、口径随时变)+ 单机 2 核部署 + 一人开发,Airbyte/Dagster/dbt/数据仓库这类重量级选件
> 全部不适配;但它们沉淀的架构契约(连接器协议、指标即代码、DAG 编排、数据可观测)恰好逐一对症
> 本系统的历史事故。`架构收敛实施方案.md` 的 P1/P2 是本蓝图的第一个里程碑。

## 0. 历史事故 → 架构缺口对照(为什么是这几层)

| 事故 | 表面原因 | 缺的架构件 |
|---|---|---|
| 笔记报表私信字段 10-13 断供,页面跟着归零 | 平台改口径 | **语义层**:指标有名字有版本,切换口径=换版本,页面与平台解耦 |
| 封面/正文等字段管道不落库,靠各品牌回填脚本 | 同步逻辑与业务逻辑耦合 | **连接器契约**:统一"拉取→标准化→落库",字段清单在契约里,漏字段=契约 diff 可见 |
| 死窗漏天、游标永久洞、锁日每小时重拉 | 无水位线,靠"成功日志"当游标 | **编排层水位线**:每(连接器,品牌)记 watermark,幂等 upsert,锁日问题整类消失 |
| cron 分 root/deploy 两处 15+ 行,改一处忘一处 | 调度即 crontab 文本 | **作业注册表**:作业+依赖+凭据前置声明式登记 |
| not_in_db=199 在日志躺了数周没人看见 | 监控靠人肉遍历 | **可观测层**:每个具名指标自动带新鲜度/量级监控(patrol L5 是手工版,升级为自动生成) |
| 每加一个品牌 ≈ 3 个脚本+3 处 crontab+若干分支 | 品牌差异散落 81 处 `brandId===N` | **租户档案**:品牌差异声明式收敛 |

## 1. 目标分层(单体内六层,不拆微服务)

```

                      │  读指标,不再各自聚合;4 组件→1 参数化  │
                      └──────────────┬───────────────────────┘
                                     │ 具名指标+版本
                      ┌──────────────▼───────────────────────┐
                      │  L5 语义层 Semantic(指标即代码)        │  metrics.yaml:
                      │  对标 dbt Semantic Layer / Cube       │  pm_leads = { formula, caliber: clue_tool_v1, since }
                      └──────────────┬───────────────────────┘
                                     │ SQL(统一事实表)
                      ┌──────────────▼───────────────────────┐
                      │  L4 指标层 Metrics(标准化事实表)       │  note_daily / account_daily /
                      │  medallion 的 silver 层               │  campaign_daily / clue_daily / lead_daily
                      └──────────────┬───────────────────────┘
                                     │ 幂等 upsert(契约键)
                      ┌──────────────▼───────────────────────┐
                      │  L3 落地层 Raw(bronze,已有雏形)        │  rawJson 按连接器约定落库
                      └──────────────┬───────────────────────┘
                                     │ pull(ctx, watermark) → 标准行
   ┌──────────────────┐  ┌───────────▼────────────────────────┐
   │ 凭据中心 Creds    │→ │  L2 连接器层 Connectors              │  mcc / partner / pro / laigu / juguang
   │ cookie 生命周期   │  │  对标 Singer/Airbyte 连接器契约      │  每平台一个模块,平台变化只改这里
   └──────────────────┘  └───────────┬────────────────────────┘
                                     │ 作业=声明式登记
                      ┌──────────────▼───────────────────────┐
                      │  L1 编排层 Orchestrator               │  作业注册表 + 依赖 + 水位线 + 回补 + 幂等锁
                      │  对标 Airflow/Prefect 的概念,单机实现  │  cron 只剩"敲钟",不再承载任何逻辑
                      └──────────────────────────────────────┘

   横切① 租户档案 TenantProfile(品牌差异声明式,81 处 brandId===N 的归宿)
   横切② 可观测 Observability(每个具名指标自动生成新鲜度/量级监控,SLO 化)
   横切③ 凭据生命周期(cookie 探活/续期/人工拖滑块事件钩子)
```

## 2. 各层契约(借鉴什么、怎么落地)

### L2 连接器契约(借鉴 Airbyte Protocol / Singer spec)

市场做法:每个数据源是一个隔离连接器,暴露 `discover → catalog → sync` 标准消息,连接器之间、
连接器与目标端互不知晓。我们取其**契约**:

```ts
interface Connector {
  id: 'mcc' | 'partner' | 'pro' | 'laigu' | 'juguang';
  credentialDeps: string[];                       // 声明依赖哪些凭据(编排层据此前置校验)
  async pull(ctx: PullCtx): Promise<RawBatch>;    // ctx={brandId, window, watermark}; 只拉取+标准化,不写业务表
}
interface RawBatch { rows: StandardRow[]; watermark: Watermark; stats: PullStats }  // rows 全带 rawJson
```

- 现有 `spark.service` 里的 API client(rtbMetrics/noteDetailList/clueAnalysisList…)+ 各 sync* 函数
  拆进 `backend/src/ingest/connectors/mcc/`;partner、pro、laigu、juguang 同理各一个目录
- 标准行 `(entity, brandId, day, keys, metrics{}, raw)`——**字段清单即契约**,新品牌/新字段漏拉在
  code review 时就是一行 diff
- 平台改口径/改端点 → 只动一个 connector 目录,上游各层无感

### L1 编排层(借鉴 Airflow/Prefect 的 DAG 概念,单机轻量实现)

- **作业注册表**(进 DB,替代 jobs.yaml 静态清单):`IngestJob { id, connectorId, brands, schedule, dependsOn, credentialPrecheck, backfillWindow }`
- **水位线表**:`Watermark { connectorId, brandId, entity, watermark, updatedAt }`——增量拉取与回补的唯一游标,
  彻底替代"用 SparkSyncLog 成功日志当锁"(锁日 bug 的机制性根因)
- **单进程 runner**:setInterval 扫表 + 依赖图就绪判断 + 并发上限 + 幂等锁;cron 里只保留一条"敲钟"和
  本机登录钩子;`trigger-sync` 变成 runner 的手动触发入口(运维习惯不变)
- 回补 = 给作业指一个历史窗口,runner 自动分片;断档自愈从"每品牌各写一套 lookback"变成注册表通用行为

### L5 语义层(借鉴 dbt Semantic Layer / Cube 的"指标即代码")

市场做法:指标定义(YAML/JS)进版本库,查询经语义层编译,任何页面/工具取同一个数。我们取其**字典**:

```yaml
# backend/src/metrics/metrics.yaml —— 页面上每个数字必须有名字
pm_leads:
  label: 私信留资数
  calibers:
    note_pm_v1:    { formula: "sum(KoxNote.pmLeads by publishTime window)", used_until: "2026-11-23(brand7)" }
    clue_tool_v1:  { formula: "sum(ClueAnalysisDaily.clueCnt by clue day)", since: { 7: "2026-11-24", 5: "2026-10-21" } }
  scope: [2, 5, 7, 8]
note_missing_backfill:
  label: 缺失笔记回补
  formula: "noteAnalysisView(all_key) − KoxNote"
```

- overview/排行/看板引用指标名,**公式只存在一处**;口径切换 = 注册新版本 + since 日期,旧版本保留
  (客户问"这个数怎么和上月不一样"→ 直接给版本 diff)
- serving 接口响应带 `metric_versions`,前端 tooltip 自动拼口径说明(替代手写 tooltip 文案)

### L4 指标层

把 overview 里内联的十几段聚合下沉成统一事实表查询(note_daily 已有雏形 KoxNoteDailyStat;
campaign_daily 已有;补 account_daily/clue_daily 归一)。**不加新表结构以外的存储**(仍是 PG 一库)。

### 横切① 租户档案 = 实施方案 P1 的 BrandProfile(不重复展开)

### 横切② 可观测(借鉴 data observability:新鲜度/量级/分布三类监控)

- patrol L1-L5 升级:监控项从 metric-registry **自动生成**——每注册一个具名指标,自动获得
  freshness(最后非零日)/volume(基线骤降)/not_in_db(完备性)三条检查,不再手工维护清单
- 告警分级:SLO 违约(页面可见数据错了)> 管道停更 > 量级漂移

## 3. 明确不采纳的(及原因)

| 市场选件 | 为什么不引入 |
|---|---|
| Airbyte / Meltano(连接器软件) | 它们的连接器跑在容器/进程外,凭据是 OAuth/密钥;我们的源需要 cookie 会话+浏览器自动化+人工拖滑块,**契约可借鉴,运行时不兼容** |
| Dagster / Airflow / Temporal | 单机 2 核跑不起调度器全家桶;DB 注册表+单进程 runner 覆盖 95% 需求,失败语义更简单 |
| dbt + 数据仓库 | 没有第二个存储引擎的运维预算;PG 一库 + 视图/事实表足够当前量级(最大单表 ~16 万行/日) |
| Kafka / 消息队列 | 无流式场景,批拉取+幂等 upsert 已够 |
| 微服务拆分 | 数据量与团队规模都不支撑;用 NestJS Module 划边界即可 |

## 4. 迁移路径(全部增量,每步可回滚;与实施方案的映射)

| 阶段 | 内容 | 借鉴来源 | 量级 |
|---|---|---|---|
| P1(已立项) | 租户档案层 | 多租户 profile 模式 | 见实施方案 |
| P2(已立项) | jobs.yaml 清单 + crontab 生成器 → 升级为 DB 作业注册表 + runner | DAG 编排 | 见实施方案 |
| P4 连接器抽取 | spark.service 拆出 connectors/mcc(先做 MCC,它覆盖 80% 流量;partner/pro/juguang 随后) | Singer/Airbyte 契约 | 1-2 个会话 |
| P5 指标字典 | metrics.yaml + overview 改引指标;口径版本留痕 | dbt SL / Cube | 1 个会话 |
| P6 可观测自动化 | patrol 检查项由 metric-registry 生成 | data observability | 半天 |

执行顺序 P1 → P2 → P4 → P5 → P6;P4 之前 P1/P2 已把品牌差异和调度收干净,连接器拆分时不再
被 81 处分支干扰。**每阶段的验收仍是那一句话:接入新品牌 = 一份档案 + 一次凭据,注册表自动长出
作业与监控。**

## 5. 参考(市场模式出处)

- 连接器契约:Airbyte Protocol / CDK、Singer spec、Meltano(2025-26 主流即"标准化连接器契约 + 低代码清单")
- 语义层:dbt Semantic Layer + MetricFlow、Cube(headless BI,指标定义 YAML 进 git)
- 编排:DAG/水位线/回补为 Airflow·Prefect·Dagster 公共概念,本方案取概念不取软件
